# Fat Functions

## Overview

Fat Functions measures every function in a folder with a deterministic script, ranks the ones that are both long and complex, and writes an interactive report. The script measures; you interpret. Judge which of the worst functions are real problems and, when the user asks, split them.

The script runs locally, uses no network, never runs or changes the measured code, and writes only into the measured folder's `.fat-functions/` folder, which gets its own `.gitignore`.

## Prerequisites

* Python 3.9 or newer: `python3` on macOS and Linux, `python` or `py -3` on Windows. The script needs nothing installed; it brings what it needs in `scripts/vendor/`.
* Code in a language the script reads: Python, JavaScript, TypeScript (with JSX and TSX), Java, C#, C and C++, Go, Kotlin, Swift, Rust, PHP, Ruby, Scala and more.

## Quick Start

Below, `<skill>` is the folder that holds this SKILL.md, and `<workspace>` is the folder to measure, usually the workspace root.

1. Run the script on the whole workspace, tests included, unless the user asks to leave something out. Use full paths, and always pass `--no-open`, so no browser window opens:

   ```bash
   python3 "<skill>/scripts/fat_functions.py" "<workspace>" --no-open
   ```

   ```powershell
   python "<skill>\scripts\fat_functions.py" "<workspace>" --no-open
   ```

2. Read the summary it prints. It holds everything the next steps need: totals, the danger zone (functions with more than 50 lines of code and complexity over 10), the five worst offenders with their file and line range, and the first files of each kind that were not fully measured. For example:

   ```text
   Fat Functions: 35 files, 669 functions, 7,040 lines of code.
   Danger zone (more than 50 lines of code and complexity over 10): 3 functions.
   Worst offenders (ranked by lines of code times complexity):
     1. send: 74 lines of code, complexity 19, Split soon (src/requests/adapters.py:590-696)
     2. build_digest_header: 68 lines of code, complexity 19, Split soon (src/requests/auth.py:126-234)
     3. resolve_redirects: 80 lines of code, complexity 15, Split soon (src/requests/sessions.py:159-280)
     4. _encode_files: 49 lines of code, complexity 21, Split now (src/requests/models.py:137-203)
     5. prepare_body: 50 lines of code, complexity 17, Split soon (src/requests/models.py:494-570)
   Not fully measured: 0 errors, 0 warnings, 1 generated file skipped:
     generated, skipped: docs/conf.py ("autogenerated")
   Report: /home/me/requests/.fat-functions/report.html
   Data: /home/me/requests/.fat-functions/report.json
   ```

   A Forgiven function's line ends its status with `, Forgiven`. With nothing skipped, the `Not fully measured:` line is left out: everything was measured.

3. Unless the user only wants the report, judge the worst offenders as described below.
4. Point the user to the interactive report as a link relative to the workspace, `[report](.fat-functions/report.html)`, unless `--out` put it elsewhere.

## Parameters Reference

| Option                  | Default                 | Effect                                                                        |
|-------------------------|-------------------------|-------------------------------------------------------------------------------|
| `path`                  | current folder          | Folder to measure                                                             |
| `--no-open`             | off: the browser opens  | Leaves the browser closed; always pass it                                     |
| `--exclude PATTERN ...` | none                    | Skips files and folders, written like `.gitignore` lines: `tests`, `src/old/` |
| `--max-loc N`           | 50                      | Danger zone: more lines of code than this                                     |
| `--max-complexity N`    | 10                      | Danger zone: cyclomatic complexity over this                                  |
| `--include-generated`   | off                     | Measures files whose first lines say they were generated                      |
| `--out FOLDER`          | `<path>/.fat-functions` | Writes the report somewhere else                                              |

Lines of code count from the signature to the end, leaving out blank lines, comments and docstrings. Complexity is 1 plus one for each `if`, `elif`, loop, `case`, `catch` or `except`, `and`/`or` (`&&`/`||`) and conditional expression, wherever it appears, comprehensions included. Statuses follow complexity: `ok` is Simple (1–5), `watch` is Watch (6–10), `soon` is Split soon (11–20), `now` is Split now (21 and over). The ranking and the danger zone are different things: the ranking orders every function by lines of code times complexity, so a top offender can sit just outside the danger zone.

## Script Reference

To leave out tests and migrations:

```bash
python3 "<skill>/scripts/fat_functions.py" "<workspace>" --no-open --exclude tests migrations
```

```powershell
python "<skill>\scripts\fat_functions.py" "<workspace>" --no-open --exclude tests migrations
```

The script writes two files into `<workspace>/.fat-functions/`:

* `report.html`: the interactive report for people, a single file that works offline.
* `report.json`: the same data for tools, needed only to look beyond the summary. It can be several megabytes; read only what you need. Its first few hundred lines hold `summary`, `thresholds` and `offenders`, the 20 worst functions with file, start and end line, lines of code, complexity, `forgiven` and status. Every function is in `tree`, found by its id: `path/to/file.py::name`, where a second function with the same name in one file gets `#2`, a third `#3`. Python methods are named without their class, so tell same-named functions apart by file and line. `errors`, `warnings` and `skipped_generated` at the end list everything not fully measured.

## Judging the Worst Offenders

The ranking is a shortlist, not a verdict. Judge the five in the summary, in their ranked order, or more from `offenders` if the user asks. For each one, read only that function, its file from start to end line, and give one of three verdicts:

* Fine as is: a long but flat lookup table or data mapping, a dispatch over many simple cases, a parser or state machine that reads best in one place, a test that checks many cases in a row.
* Could be tidied: one clear part worth pulling out, and the rest reads well.
* Worth splitting: two or more independent parts worth pulling out, or nesting three or more levels deep. Typical signs: several jobs in one function (reading input, deciding, formatting, writing), repeated blocks, a long parameter list, code that is hard to test on its own.

Functions marked Forgiven in the summary (`forgiven: true` in `report.json`) carry a `#lizard forgive` comment: the team accepted them on purpose. Mention them, but do not suggest splitting them unless the user asks.

Open the answer with one line: the totals and how many functions are in the danger zone. Then give a short list in ranked order. For each function give a link to its file and line, relative to the workspace (for example `[send](src/requests/adapters.py#L590)`), its lines of code and complexity, the verdict and one sentence why. End with one sentence on where to start, which need not be the first. Then mention anything not fully measured: for a skipped generated file, offer to measure it with `--include-generated`, but rerun only if the user asks.

## Splitting a Function

Only when the user asks. "The worst one" means the first in the summary, unless the user names another. Keep the split a pure move: behavior stays the same, and bugs or dead code you notice are pointed out separately, not fixed in the same change.

1. Read the function, what it calls, and the tests that cover it. Find the test command: prefer the plainest one that runs the whole suite locally (`pytest`, `npm test`, `go test ./...`), as given in the README, `pyproject.toml`, `package.json`, a Makefile or the CI configuration.
2. Propose the split, then stop and ask before changing any file. Name the seams with their line ranges (guard clauses at the top, the body of a loop, each branch of a large conditional, or validation, calculation and output as separate steps). Sketch the new shape in short code: private helpers next to the original, in the file's style. Say how behavior stays the same, estimate the new lines of code and complexity, and name the test command, or say you could not find one.
3. Once the user agrees, make the change and run the tests. If test tools or the project's dependencies are not installed, ask the user before installing anything or creating an environment.
4. Run the script again with the same arguments as before and report how the function's lines of code and complexity, and the new functions', compare with before.

## Troubleshooting

| Problem                                             | What to do                                                                            |
|-----------------------------------------------------|---------------------------------------------------------------------------------------|
| `python` is not found or opens the Microsoft Store  | Try `python3` or `py -3`; if none works, Python 3.9 or newer needs installing.        |
| `not a folder` and exit code 2                      | The path does not exist or is a file; pass the workspace folder.                      |
| 0 functions                                         | No supported source files, or all excluded or ignored by `.gitignore`.                |
| A file the user wrote appears as generated, skipped | Its first 10 lines contain a generated-code notice; rerun with `--include-generated`. |
| Vendored or third-party code dominates the list     | Rerun with `--exclude` for those folders, such as `--exclude vendor third_party`.     |
| The run takes long                                  | About 7,000 lines of code a second; a 400,000-line project takes about a minute.      |
